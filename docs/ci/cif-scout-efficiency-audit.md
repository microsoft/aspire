Review draft for `microsoft/aspire`. This document does not change the live Scout prompt, runbook, tools, or triggers. It covers saving generated evidence and reusing completed CI evidence. The manual start was intentional; no scheduling change is proposed.

## Copy-ready Scout prompt edits

Apply these only to the Scout section of the current saved prompt. Keep the shared rules, startup runbook check, and unrelated settings intact. Count the resulting full prompt against the 12,000-character limit before applying.

### Insert after the `scout/cursor.json` paragraph

```text
Generate JSON once and measure its UTF-8 bytes before publishing (head <=28672 plus 4096 reserve; evidence shards <=16384). Pass generated bytes unchanged only through an authorized, supported path that preserves the required lease fence and matching ETag CAS on replacements. Pin readback to the committed ETag and verify bytes before advancing. No manual transcription of generated bulk JSON, unfenced head replacement, or retry of a denied path. If blocked, leave the current head and history intact, save independent small fenced records only when safe, and report the blocked record, exact continuation and unresolved effect. No migration without approval. Use the trusted server session ID in receipts or record unknown.
```

### Replace numbered steps 2 and 3

```text
2. Scan the last 24h first, then resume fairly across streams toward 7d metrics and 14d frequency; incomplete coverage is pending. List by creation time with 2h overlap, refresh outstanding runs, and periodically reconcile 14d for late retries. Discover current status and attempt even on evidence reuse; do not advance past unread or unpersisted observations.
3. Use verified existing population and ledger references to reuse completed evidence by provider/workflow/run ID/attempt. Reuse only the coverage actually verified (conclusion, jobs, or named failure evidence); a receipt or coarse signature does not settle missing jobs, logs or causes. Fetch gaps, pending or newly discovered attempts, and contradictory evidence. For failure/timed_out or attempt>1, inspect attempt 1 from verified evidence or Actions, including every attempt-1 PR ci.yml failure even if a retry went green. Keep approval gates separate from test failures. Persist success/pending population and dedupe observations by provider/run/attempt/signature. Do not cache issue eligibility, ownership, PR heads or mutable conclusions.
```

### Append to numbered step 4

```text
Unknown cause is not P0 by itself. Use the saved P0 criteria over any broader addendum wording, and keep unresolved attribution explicit.
```

### CI Insights: leave it optional

CI Insights MCP wasn't exposed in the audited session or listed in the hosted tool catalog. No query or refresh measurement was possible. If it becomes available, use it for streams and attempts it demonstrably covers, behind its reported refresh watermark. The expected refresh interval is about 15 minutes, not a measured guarantee. Use live GitHub for newer, missing, incomplete, or contradictory records and before decisions that depend on current state. Missing index data is never green. No CI Insights dependency or grant change is needed for evidence reuse.

## What to compare on a later manual run

Record cache hits by evidence level, attempt/job/log reads made or avoided, publication attempts and repairs, and elapsed time. Review against comparable input volume. Confirm that a green retry still retains its attempt-one failure, an approval gate stays separate, and pending or incomplete evidence survives the checkpoint. A changed ETag or uncertain write must still stop cursor advancement until reconciled. The prompt edits cannot supply a missing exact-byte fenced transport; verify that path separately before relying on it.
